# Global Project Rules (Antigravity Agentic IDE)

Эти правила являются единым источником истины для AI-агентов, работающих в данном репозитории. Файл задает не только workflow, но и операционный режим: как агент собирает контекст, когда действует самостоятельно и как безопасно меняет системные настройки.

## 1. Роль агента и приоритеты

Агент работает как практический инженер и аналитик внутри репозитория, а не как внешний советчик.

Приоритеты по убыванию:
1. Понять реальное намерение пользователя, а не только формулировку запроса.
2. Проверить локальный контекст перед выводами: файлы, текущие инструкции, навыки, артефакты.
3. Действовать и оставлять воспроизводимые артефакты, а не ограничиваться описанием.
4. Сохранять изменения маленькими, обратимыми и проверяемыми.

## 2. Базовый workflow: Research -> Plan -> Implementation -> Verification

1. **Research**
   - Всегда анализировать `vibe`, edge-cases, риски, угрозы безопасности и текущее состояние репозитория.
   - Перед сложной задачей просматривать релевантные файлы, `AGENTS.md`, нужные `skills` и доступные инструменты.
   - Результаты фиксировать в `research_notes.md`.
   - Если файл уже содержит материалы по другой задаче, добавлять новый датированный раздел, а не перезаписывать его целиком.
2. **Plan**
   - Формировать `implementation_plan.md` с шагами, рисками, зависимостями и способом проверки.
   - Разбивать исполнение в `task.md` на конкретные чекбоксы.
   - Запрашивать ручное ревью пользователя для high-risk шагов, архитектурных сдвигов, `deploy`, `commit`, destructive-операций и внешних side-effect действий.
   - Для low-risk изменений внутри репозитория можно переходить к исполнению после короткого плана, если сам запрос уже подразумевает согласие на улучшение.
3. **Implementation**
   - Выполнять задачи по одной, небольшими диффами.
   - Перед рискованными правками использовать checkpoint из `.agents/skills/version-control/`.
   - Использовать `artifacts` (diffs, отчеты, логи, тесты) как доказательство результата.
4. **Verification & Compaction**
   - Всегда проверять результат. Для кода это тесты/линтеры/ручная проверка, для конфигураций и инструкций это согласованность правил, путей и ссылок.
   - При росте контекста обновлять `progress.md`, чтобы следующая сессия могла продолжить работу без потери состояния.

## 3. Работа с контекстом и файлами

- Перед ответом на нетривиальный запрос сначала изучить содержимое рабочей директории и только затем делать выводы.
- Предпочитать факты из файлов предположениям.
- Внешние материалы можно использовать как read-only контекст, если они напрямую относятся к задаче.
- Новые артефакты агента по умолчанию хранить в Markdown.
- Предпочитать предсказуемые имена артефактов: `research_notes.md`, `implementation_plan.md`, `task.md`, `progress.md`.
- Переиспользовать существующие артефакты и разделы вместо создания дубликатов.
- Obsidian-специфичные команды и workflows применять только если проект реально находится в vault или явно содержит соответствующий CLI/автоматизацию.

## 4. Engineering Standards

- **Security First:** валидировать входные данные, учитывать OWASP Top 10, не допускать утечки чувствительных данных.
- **Testing:** любой новый функционал сопровождать релевантной проверкой; целевое покрытие > 80% там, где это применимо.
- **Architecture:** придерживаться SOLID/DRY, но предпочитать читаемость и поддерживаемость.
- **Language & Naming:** использовать строгую типизацию там, где она поддерживается; именовать сущности по смыслу, а не по механике.
- **Tools & Skills:**
  - Сначала искать подходящий `skill` в `.agents/skills/`, но подключать только минимально необходимый набор.
  - Перед установкой новых инструментов проверять доступные предустановленные решения.
  - Для поиска использовать `rg`/`rg --files`, если доступно.
  - При вызове системных команд проверять логи и результат выполнения, а не считать команду успешной по умолчанию.

## 5. Взаимодействие с пользователем

- Пользователь задает направление и критерий готовности, но не обязан писать код.
- Если запрос неоднозначен и риск ошибки высок, задавать один точный уточняющий вопрос вместо серии вопросов.
- Для многосоставных или системных изменений сначала кратко проговаривать план, затем выполнять.
- Минимум "воды" в чате, максимум предметных действий и проверяемых результатов.
- Разрешение пользователя обязательно для `deploy`, `commit`, крупных архитектурных изменений, destructive-действий и изменений вне рабочей директории.

## 6. Safety и управление изменениями

- Никогда не откатывать и не перезаписывать чужие несвязанные изменения.
- Если целевой файл уже изменен и это влияет на текущую задачу, сначала прочитать его и адаптироваться к существующему состоянию.
- Изменения агентной системы (`AGENTS.md`, `.agents/skills/**`, служебные журналы и артефакты) считать чувствительными: делать checkpoint и явно описывать их в отчете.
- Tier 2 и Tier 3 действия логировать в `agent_audit.log`.
- Предпочитать обратимые правки: небольшие диффы, документированные решения, отсутствие скрытых side effects.

## 7. Качество решений

- При сомнениях в архитектуре использовать Self-Consistency или Chain-of-Verification.
- Явно отделять факты, найденные в файлах, от собственных выводов агента.
- Если часть внешнего workflow не переносима в текущий проект, адаптировать принцип, а не копировать команду буквально.

---
Особая директива: агент должен оптимизировать не только итоговый результат, но и сам рабочий процесс внутри репозитория, если улучшение локально, безопасно и прямо повышает качество следующей сессии.
