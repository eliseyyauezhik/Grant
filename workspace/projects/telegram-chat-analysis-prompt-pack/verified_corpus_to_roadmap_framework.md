# Framework: Corpus -> Проверка -> Приоритизация -> План

## Назначение

Этот framework превращает Telegram/chat/database corpus не просто в summary, а в проверяемый набор знаний и план внедрения. Логика одна и та же:

1. извлечь утверждения и high-signal patterns;
2. проверить ключевые тезисы по первичным источникам;
3. разложить знания по корзинам достоверности;
4. проранжировать их по практической ценности;
5. собрать удобную библиотеку знаний и roadmap внедрения.

## Приоритет источников

Использовать источники по убыванию доверия:

1. официальная документация, спецификации, API reference;
2. официальный changelog, releases, release policy;
3. официальные issues, комментарии maintainers, provider policy pages;
4. first-party blog posts и FAQ;
5. сам corpus;
6. вторичные пересказы и форумные summary.

Правило: источники уровней `5-6` не могут опровергать `1-3`. Они только подсказывают, что именно нужно проверить.

## Корзины достоверности

### `проверено`

Критерий:
- тезис подтвержден хотя бы одним первичным источником;
- нет актуального официального противоречия;
- формулировка очищена от лишней интерпретации.

Использование:
- можно включать в roadmap как опорную практику;
- можно переносить в reusable skill/reference;
- можно нормализовывать в библиотеку знаний vault.

### `вероятно, но не проверено`

Критерий:
- тезис выглядит правдоподобным и полезным;
- есть повторяемый сигнал в corpus;
- но первичная проверка пока неполная, косвенная или устаревающая.

Использование:
- можно держать в backlog экспериментов;
- нельзя продвигать как твердое operating rule.

### `спорно или быстро устаревает`

Критерий:
- тезис time-sensitive, спорный, конфликтный или опирается на слабые источники;
- или официальные источники подтверждают только часть формулировки.

Использование:
- хранить как зону осторожности;
- не делать основой архитектурных решений без новой проверки.

## Дополнительная отметка по нашей среде

Помимо корзины достоверности, для каждого важного item полезно ставить вторую отметку:

- `проверено по первичным источникам`
- `не проверено в нашей среде`
- `проверено в нашей среде`

Это позволяет не смешивать два разных вопроса:

1. правда ли это по официальным источникам;
2. подтверждено ли это именно в нашей системе и на наших данных.

## Рубрика ранжирования

Каждый item оценивается по шкале `1..5`.

### Положительные оси

- `сила_подтверждения`
  - `5`: проверено
  - `3`: вероятно, но не проверено
  - `1`: спорно или быстро устаревает
- `применимость`
  - насколько знание применимо к нашему текущему `OpenClaw` и смежным проектам
- `влияние`
  - насколько сильно item меняет стабильность, качество, скорость или стоимость работы

### Отрицательные оси

- `устаревание`
  - насколько быстро item теряет актуальность
- `затраты`
  - насколько дорого внедрять или проверять item в реальной среде

## Формула приоритета

```text
приоритет =
  (сила_подтверждения * 0.30 +
   применимость      * 0.25 +
   влияние           * 0.25 +
   (6 - устаревание) * 0.10 +
   (6 - затраты)     * 0.10) * 20
```

Интерпретация:

- `85-100`: делать в первую очередь, это почти опорный слой
- `70-84`: важный следующий слой
- `50-69`: осмысленный backlog или controlled experiment
- `<50`: не делать default-практикой без новой проверки

## Обязательные выходы

Минимальный набор артефактов:

1. `реестр проверки`
   - тезис
   - уровень источника
   - первичный источник
   - корзина достоверности
   - отметка по нашей среде
   - практический вывод
2. `реестр приоритетов`
   - итоговый score
   - применимость
   - влияние
   - устаревание
   - затраты
3. `человекочитаемый roadmap`
   - что устойчиво
   - что полезно, но пока не подтверждено
   - что лучше держать как эксперимент
   - какая последовательность изменений следует из этого
4. `открытые вопросы`
   - что ещё нужно проверить позже

## Рекомендуемая последовательность

1. Переиспользовать уже существующие структурированные outputs, если они есть.
2. Проверять сначала только roadmap-relevant claims, а не каждый абзац corpus.
3. Сначала раскладывать по корзинам достоверности.
4. Только потом ранжировать.
5. Сначала собрать библиотеку знаний и план.
6. И лишь затем упаковывать workflow в skill, KB artifact или automation path.
