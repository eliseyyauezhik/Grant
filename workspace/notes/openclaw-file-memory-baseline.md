# OpenClaw File-Memory Baseline

## Зачем это нужно

Для текущего `OpenClaw` самый безопасный и практичный следующий шаг модернизации — не “умная память”, а простая файловая память.

Смысл:

- важные знания не должны оставаться только в Telegram;
- полезные выводы должны попадать в файлы;
- агенту нужен устойчивый контекст, а не надежда на длинный чат.

## Что входит в baseline

Минимальный стандарт:

1. `daily notes`
- короткая фиксация того, что происходило сегодня;
- что изменили;
- что проверили;
- какие проблемы остались.

2. `MEMORY.md`
- только устойчивые и важные факты;
- без мусора и временных гипотез;
- это не лог, а сжатая рабочая память.

3. curated files
- отдельные короткие файлы по важным темам:
  - доступы и контуры
  - known issues
  - принятые решения
  - roadmap

4. write-back после полезной сессии
- если диалог реально дал решение, итог переносится в файл;
- если это только размышления, в постоянную память не записывать.

## Что не входит в baseline

Пока не считать обязательным:

- embeddings
- vector DB
- long-history Telegram ingest
- Telegram Business как memory layer
- локальные маленькие модели как fallback memory engine

Это можно пробовать позже, но не делать первой модернизацией.

## Рекомендуемая структура

Простой вариант:

- `daily notes`
- `MEMORY.md`
- `openclaw-known-issues.md`
- `openclaw-decisions.md`
- `openclaw-roadmap.md`

## Правило записи в память

В `MEMORY.md` и curated files попадает только то, что:

- подтверждено локально или первичными источниками;
- реально помогает в следующих сессиях;
- не является разовой технической мелочью.

Не писать туда:

- длинные сырые переписки;
- непроверенные идеи;
- устаревающие советы без версии;
- секреты и ключи.

## Write-Back Template

После полезной сессии записывать коротко:

1. Что изменили
2. Что подтвердили
3. Что осталось открытым
4. Нужно ли это в `MEMORY.md`, `daily notes` или только в backlog

## Что делать следующим шагом

После принятия этого baseline:

1. создать реальный `MEMORY.md` для `OpenClaw`;
2. завести ежедневную короткую operational note;
3. вынести known issues из диалогов в curated file;
4. только потом решать, нужен ли embeddings-layer.

## Связь с общей траекторией

Этот baseline соответствует уже собранной траектории:

- сначала version discipline;
- потом runtime correctness;
- потом управляемый Telegram surface;
- потом file-memory baseline;
- и только потом corpus intelligence и experiments.
