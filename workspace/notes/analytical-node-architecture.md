# Архитектура Аналитического Узла

## Кратко

Многоэтапная процедура `corpus -> проверка -> triage -> ranking -> roadmap` должна стать не разовым кейсом по Telegram, а ядром аналитического слоя всей AI-системы. Этот слой должен превращать сырые входящие данные в проверенные знания, приоритеты, сигналы и следующие шаги, а затем передавать их в vault, dashboard и исполнительные агенты.

## Зачем нужен Аналитический Узел

Сейчас в системе уже есть правильные базовые слои:

- `My Dashboard` как front door;
- `Obsidian vault` как долговременная память;
- агентный слой как processing/execution layer;
- внешние адаптеры вроде `OpenClaw`, Telegram, NotebookLM, YouTube и web.

Не хватает отдельного устойчивого аналитического механизма, который:

- читает новые corpora и материалы;
- отделяет факты от шума;
- проверяет важные тезисы по первичным источникам;
- ранжирует знания по ценности;
- делает write-back в vault;
- превращает знания в сигналы для проактивной помощи.

## Место в общей системе

Рекомендуемая схема:

`My Dashboard -> Личный ИИ-оркестратор -> Аналитический Узел -> Vault / Исполнительные агенты / Интеграции`

Расшифровка ролей:

- `My Dashboard`
  - пользовательский вход;
  - обзор проектов, inbox, alerts и next steps.
- `Личный ИИ-оркестратор`
  - понимает ваши интересы и проектные цели;
  - решает, когда звать исследовательский, исполнительный или monitoring-поток;
  - читает сигналы из vault и предлагает следующие шаги.
- `Аналитический Узел`
  - превращает новые данные в проверенные знания и ranked backlog.
- `Vault`
  - system of record для долговременной памяти.
- `OpenClaw`, subagents, workflows, `n8n`
  - исполнительные узлы и адаптеры, но не источник истины.

## Канонический pipeline

### 1. Intake

Новые данные попадают из:

- Telegram;
- чатов;
- документов;
- видео;
- голосовых;
- ссылок;
- базы сообщений;
- workflow outputs;
- ручных заметок.

### 2. Normalization

Каждое входящее приводится к единому пакету:

- источник;
- время;
- тип;
- проект;
- связь с существующими сущностями;
- сырой контент или указатель на него.

### 3. Corpus processing

Для крупных массивов данных запускается staged-пайплайн:

1. извлечение claims и signal patterns;
2. consolidation по темам;
3. первичная аналитическая выжимка.

### 4. Verification

Ключевые тезисы проверяются по первичным источникам:

- официальная документация;
- API/spec;
- official releases/changelog;
- official issues и policy pages.

### 5. Triage

Каждый item попадает в одну из корзин:

- `проверено`;
- `вероятно, но не проверено`;
- `спорно или быстро устаревает`.

Дополнительно ставится отметка:

- `проверено по первичным источникам`;
- `не проверено в нашей среде`;
- `проверено в нашей среде`.

### 6. Ranking

Знания ранжируются по:

- силе подтверждения;
- применимости;
- влиянию;
- устареванию;
- затратам.

### 7. Write-back

Результат ложится в vault не как сырой чат, а как структурированный knowledge layer:

- библиотека проверенных знаний;
- roadmap;
- KB notes;
- обновления project memory;
- новые задачи или alerts.

### 8. Proactive loop

После write-back система должна уметь:

- замечать новые подтвержденные знания;
- видеть изменения приоритетов;
- связывать знания с проектами и областями развития;
- предлагать конкретные следующие шаги;
- при необходимости запускать нужного исполнителя.

## Что хранить в Obsidian

`Obsidian vault` должен быть system of record и для аналитического слоя.

Рекомендуемая раскладка:

- `notes/inbox/`
  - сырой вход и новые captures
- `projects/`
  - активные прогоны, roadmap-документы, проектные регистры
- `notes/sources/`
  - Markdown-конспекты и source notes по первичным источникам
- `notes/decisions/`
  - устойчивые архитектурные выводы
- `notes/reports/` или project report layer
  - weekly synthesis, обзорные сводки, risk reports

Принцип:

- бинарные материалы и внешние сервисы не являются памятью сами по себе;
- памятью становится только Markdown-след, связанный с проектом, источниками и выводами.

## Роли субагентов внутри Узла

Минимально полезный набор ролей:

- `сборщик`
  - забирает и нормализует входящее
- `экстрактор`
  - вытаскивает claims, entities, timelines
- `верификатор`
  - проверяет ключевые тезисы по первичным источникам
- `библиотекарь`
  - делает write-back в vault и связывает с project memory
- `стратег`
  - ранжирует, собирает roadmap и next steps
- `проактивный ассистент`
  - читает обновления из библиотеки и предлагает, что делать дальше

## Отношение к OpenClaw

`OpenClaw` в этой схеме — важный исполнительный и conversational node, но не system of record.

Это значит:

- знания не должны оставаться только внутри OpenClaw sessions;
- важные выводы должны возвращаться в vault;
- `OpenClaw` может быть одним из агентных исполнителей в интересах личного ИИ-оркестратора;
- сам оркестратор не должен сводиться только к OpenClaw.

## Первый рабочий прототип Узла

Текущий Telegram prompt-pack кейс уже дал первый рабочий каркас:

- staged extraction;
- external verification;
- evidence triage;
- ranking;
- human-readable knowledge library;
- roadmap;
- reusable skill.

То есть прототип Узла уже есть. Теперь его нужно не потерять и расширить на другие типы corpora.

## Что должен делать проактивный слой

Проактивная система помощи должна читать не сырой шум, а именно библиотеку проверенных знаний и project memory. Ее задача:

- замечать полезные изменения;
- предлагать новые траектории развития;
- напоминать о рисках и возможностях;
- подсказывать, какой агент или workflow сейчас уместен;
- собирать предложения в формате, понятном человеку, а не только другому агенту.

Важно:

- проактивность не означает самовольное вмешательство;
- по умолчанию система должна предлагать, готовить и маршрутизировать;
- реальные действия без отдельного запроса допустимы только в заранее разрешенных границах.

## Рекомендуемая дорожная карта

### Ближайший слой

- закрепить единый framework `corpus -> проверка -> triage -> ranking -> roadmap`;
- перевести user-facing outputs на русский;
- нормализовать output shape для повторного использования.

### Следующий слой

- встроить write-back из corpus runs в vault notes;
- завести реестр проверенных знаний по проектам;
- привязать его к `project_id` и dashboard.

### После этого

- настроить weekly synthesis loop по новым знаниям;
- сделать сигналы для личного ИИ-оркестратора;
- связать сигналы с executor nodes, включая `OpenClaw`.
